# Hermes Auto-Update

Hands-off Hermes updates via a system-cron job outside the gateway process tree; notifies Telegram only for real outcomes. Battle-tested across 20+ live cycles and six adversarial review rounds.

## Architecture (non-negotiable)

**System cron, never hermes cron.** A hermes-cron job lives inside the gateway process tree — the root of every update race: the updater can only signal a restart after it exits, waiting inside the script deadlocks, and the fleet check reports STALE. Out of the tree the updater drains the gateway, restarts it via systemd, and verifies the fleet itself before exiting, so the script can verify synchronously.

## Rescheduling (changing the tick cadence)

Changing the cron frequency is a three-place edit, all verified in one pass:
1. **crontab**: edit the line via `crontab -l | sed ... | crontab -` and print `crontab -l` after — the echoed crontab is the verification, not the sed's exit code.
2. **SKILL.md**: update the Cron line in Procedure (cadence + the rescale note for alert counters — the re-alert interval is counted in TICKS, so 12 ticks at 3h = 36h).
3. **Grep the script for cadence-coupled logic** (`24`, `12`, `% N`, hourly comments): the dedup counters count TICKS, not hours, and the script has no hourly hard-coding otherwise — but the SKILL.md note must say the re-alert period in wall-clock terms so a future reader does not rescale the wrong constant.

## Procedure

1. **Script** `~/.hermes/scripts/auto_update.sh`, ordered so nothing is called before it is defined:
   1. `set -u`; guard `HOME` (`${HOME:-$(getent passwd "$(id -u)" | cut -d: -f6)}`); `export XDG_RUNTIME_DIR=/run/user/$(id -u)`.
   2. `notify()` before any call site, message as `$1` (creds from `~/.hermes/.env`, proxy via `$TG_PROXY`).
   3. Resolve hermes by absolute path (candidates, then PATH); abort with a notification if absent.
   4. `flock -n` on `$HOME/.hermes/state/auto_update/auto_update.lock`; rotate the log at 5 MB.
   5. `update --check` → gate on BOTH exit code and output text.
   6. Up to date → one trace line, exit 0, silent.
   7. Update available → if `AU_APPLY=1` continue, else log + print "not applied" and exit 0 (report-only). When applying: `update --yes`, log `tail -40`, classify.
   8. **Classification** (receipt-first, freshness-gated): capture `RUN_STARTED` BEFORE `--yes`; trust `latest.json`'s `outcome` only when `finished_at >= RUN_STARTED - 5s`. Set `drain_pending` BEFORE the catch-up poll. `exit=0 + fresh success` → ✓. `exit=0 + fresh partial` → poll for gateway catch-up (`code_sha` == HEAD AND `is-active`); timeout is NOT failure (drain may take 30 min) → neutral exit 0, marker carries the obligation. `exit≠0 + fresh success/partial + SHA advanced` → restart race, ✓ with note. `exit=0 + stale receipt + "Already up to date"` → silent no-op. Anything else → ✗ failure.
   9. Real failure → ✗ with `consec_real_fails` (alert on 1st, re-alert every 12th); every success path resets it.
   10. Counters in state files: `consec_check_fails` (3/24), `consec_notify_fails` (3/24, also counts missing credentials). All reads via a numeric sanitizer.
2. **Cron**: `23 3 * * * set -a; [ -f $HOME/.hermes/scripts/auto_update.env ] && . $HOME/.hermes/scripts/auto_update.env; set +a; AU_APPLY=1 <script>` (daily 03:23, off-the-hour; history: hourly → every-3h 2026-09-15 → daily 2026-09-16, user preference is less frequent). **`AU_APPLY=1` is required** — without it the run only reports that an update is available. `set -a` around the source is required too: without it the env file delivers NOTHING to the script (the updater never sources the file itself), which is invisible because the flag — prefixed to the script — still arrives. Alert cadences assume a ~24h tick interval — rescale if the schedule changes.
3. **Gate the release**: from the *extracted* bundle run `bash scripts/release_gate.sh` (doc pointers + matrix + every probe + teeth) and require PASS. The gate runs for minutes (full matrix + self-seeding probes + teeth) — launch it `background=true` with `notify=true` or a raised timeout; the default foreground call dies mid-matrix at the tool timeout and reports nothing. Then — **Verify with the hermetic harness** in `verify/` (stub hermes/curl/systemctl, stub FIRST in the candidate list): run it before and after every patch and require 0 failed — its own tally is the truth, never restate counts in prose. Time-based waits have env knobs (`AU_POLL_EVERY`/`AU_POLL_TRIES`/`AU_SETTLE_SECONDS`/`AU_UPDATE_TIMEOUT`/`AU_UPDATE_KILL`/`AU_CHECK_TIMEOUT`) and the matrix's `run()` must set them.
4. **Verify real updates** via the receipt's `pre_update.short_sha` vs `post_update.short_sha` (advancing SHA = a real install) and `hermes gateway status`.
5. **Audit the schedule, not just the last run.** Enumerate the fire times the cron expression implies for a window, extract the actual tick timestamps from the log, and diff them. A missing window means the scheduler never fired — silent by construction (see the WSL cron pitfall); a long run of ticks with no "update available" means the check banner changed and the stall guard should have alerted. Answer "is the cron healthy?" with the window count and any misses, never with "looks fine".

## Pitfalls

**Upstream contract**
- `update --check` exits 0 whether or not an update exists, and 1 on fetch failures. Gate on text, but treat a nonzero exit as transient — never as "up to date", or a failed check reads as current.
- `update --yes` can exit 1 while printing "Update complete": the install landed but the fleet check ran mid-drain. Never classify by exit code or human text alone.
- The receipt freezes at finalize: a drain finishing later leaves `fleet: stale` plus a lingering `fleet_restart_pending` warning. The next `--yes` (even up-to-date) discharges it. Don't hand-delete the marker.
- Pull-stage failures (merge conflict, syntax guard, SIGKILL) exit WITHOUT finalizing, so `latest.json` still holds the PREVIOUS run's `success`. Freshness-gate every read; "stale" means "no evidence about this run".
- `receipt=success` carries a SHA-verified fleet snapshot (the updater's post-restart matrix compares live `code_sha` against the checkout) — it is not "no verification", but it does not prove the process stayed up. Keep `drain_pending` through the receipt and clear only after your own recheck.
- Text-gating has a stall mode: a reworded banner makes every tick read "up to date" forever, silently. Only "Already up to date" is legitimate; anything else is inconclusive and must alert.

**Classification rules**
- A success-shaped branch must key on MACHINE fields, never text: compare `pre_update.short_sha` vs `post_update.short_sha` (advance = landed), with text only as fallback. Dropping the text gate entirely is equally wrong — it turns "deps failed after pull" into a false success.
- When two call sites must agree on the same invariant ("is the gateway healthy?", "is this delivered?"), implement it ONCE and call it from both. Two hand-rolled copies drift: a weaker check added to one branch silently re-admits the false positive the other branch was hardened against. Divergence between callers of the same predicate is the bug vector — extract the predicate before adding the second check.
- A marker may be cleared ONLY after the invariant it exists for is positively verified (sha match + is-active), never on a verdict that merely "isn't a failure". Sweep EVERY success-shaped exit when auditing a flag's lifecycle. A receipt proving an install was ISSUED (or that some other updater finished) is not evidence that THIS gateway is healthy on the new code.
- "Next tick re-verifies" must be CODE: the no-update path exits before `--yes`, so a cross-tick promise needs a state file the other path actually reads. A hot streak can delete the no-update path for days — obligations must also run in-line at the end of update ticks.
- Set a "flag it so the next run notices" marker BEFORE the risky wait, not only on its timeout — an interruption mid-wait must leave the install flagged.
- Reset a consec-counter only on CONCLUSIVE outcomes. Resetting before the branch that increments it makes that branch always read 0: a dead guard whose alert can never fire. The converse bites too: a no-op ("nothing to update") tick IS a conclusive success — reset the failure counter there as well, or a later, unrelated failure gets deduped against a stale count and never alerts. Enumerate every conclusive-success exit and reset at each.
- Sanitize every counter read (strip non-digits, clamp, garbage → 0 and overwrite). Under `set -u`, `$((m+1))` on a corrupt file aborts the script before any alert — the updater silences itself.
- Clamp by LENGTH before arithmetic, never after. A long all-digit string does not abort: bash `$((10#999…9))` overflows SILENTLY to a small — even NEGATIVE — value with rc=0, and a clamp applied AFTER the arithmetic never sees it (the clamp checks the length of an already-evaluated value). Measured on the arithmetic-first order: `18446744073709551619` → counter 4, `18446744073709551611` → counter −4, when the correct value is 1 in both cases. A negative counter matches no `-eq 3` and no `% 24`, so the alert it guards is delayed forever. Write `if [ "${#v}" -gt 6 ]; then v=0; fi` BEFORE `v=$((10#$v))`, and assert the exact post-run value (a `<= max` bound passes 4, which is the bug).
- Never count failures by grepping an ever-growing log; use a state file. (`grep -c ... || echo 0` yields two lines at zero, breaking `[`.)

**Testing**
- New logic must enter the matrix the SAME round it enters the script, or the green matrix lies. Prove teeth destructively: force the new condition to 0, then to 1 — a scenario must fail each way. `bash -n` the neutered copy first, or a syntax error will masquerade as coverage.
- A probe must drive a branch that actually READS the thing it guards. A counter-corruption probe that only ran the up-to-date path — which WRITES a counter without reading one — reported PASS on a build with the sanitizer removed: zero teeth, and it looked like coverage. Choose the scenario by asking "which branch reads this?", then confirm by neutering. The release gate now runs this check mechanically (step 4/4: each guard's known neuter is fed to its probe, which must FAIL) — when you add a new guard, add its neuter to the gate the same round.
- Pick the assertion's OBSERVABLE so it separates the two builds. Bash replaces a failed `$((10#…))` with 1 — a valid-looking number — so an end-value assertion cannot distinguish a sanitized read from a broken one; the arithmetic error escaping to stderr is the observable that does. When both outcomes land in the valid domain, assert the side channel (stderr), not the value, and verify the assertion bidirectionally (sanitized → PASS, neutered → FAIL).
- Neuter the SOURCE and pass its path to the probe, never a pre-neutered harness copy: a probe that self-seeds rebuilds `$HARNESS_ROOT` from `$1` and silently overwrites whatever you patched there, so the teeth run against the UNBROKEN code and "pass". Copy the source, `sed` the neuter into the copy, `bash -n` it, hand the copy to the probe.
- A hermetic harness must be hermetic against its OWN users, not only its stubs. A shared harness root with no lock reports a FALSE RED under concurrency: two runs sharing one `HARNESS_ROOT` delete each other's home directory, and the same unchanged commit scored 55/7 and 56/6 while a clean single run scored 62/0. A harness that cannot distinguish "the code is broken" from "someone else is mid-run" is worse than none — the red verdict is the point. `flock` the harness root in BOTH the setup and the matrix, and fail loudly rather than interleave. Also `unset` the knobs (`TG_PROXY`, `AU_REPO_DIR`, `AU_GATEWAY_STATE`, `AU_HERMES_BIN`, `AU_APPLY`, the poll/timeout knobs) before running scenarios: a leaked value makes a scenario borrow the host's real configuration, and a leftover `export AU_APPLY=1` masks a probe that forgot to opt in.
- Support scripts must locate their siblings from their own directory (`HERE="$(cd "$(dirname "$0")" && pwd)"`, then `"$HERE/../verify/stub_setup.sh"`) so they run from any cwd, and each must build the fixtures it needs rather than assuming the matrix already ran (`reset_home` before a sweep that deletes `$HOME`). `HERE/../<dir>` is positional: the script must sit in its own subdirectory for the `..` to resolve — when a sibling "cannot be found", first check where YOU placed the script before blaming the tool.
- A "hermetic" harness is only as sealed as its path assumptions. Health-check targets must be env-overridable (`AU_REPO_DIR`/`AU_GATEWAY_STATE`/`AU_GATEWAY_UNIT`) and the test must point them at deliberately sick fixtures — otherwise green scenarios silently borrow the real machine's health.
- Name shared variables as the ecosystem expects (the harness rewrites `REPO=`; a differently-named var is invisible and the scenario falls back to the real machine).
- After fixing a hardcoded path or any class of bug, grep the whole file for every other use site — a class fix applied to one site is a half fix.
- A test mode may differ from the real artifact ONLY in the field under test; never let a mode name leak into a machine-read field (a fixture writing `outcome: "partial_sha"` fails for the wrong reason and masks the branch).
- Any time-based wait needs an env knob AND that knob must be set in the matrix helper, or every scenario silently pays the full wait.
- Bound every external call made while holding the lock. An uncapped call that hangs does not merely fail: it holds the flock, so every later tick skips and only the phase you instrumented gets counted as a failure. `hermes update --yes` may legitimately block ~30 min (upstream `restart_after_turn_timeout=1800`), so cap above it (default 3600s) and treat timeout exits 124/137 as WEDGED: alert, keep the marker, exit non-zero. `update --check` needs a cap too (default 300s).
- A test that cannot interrupt the code (kill mid-wait) cannot see interruption bugs; a harness proves only the branches you thought about.
- Keep the reviewer's own harness in `verify/` and prefer it to hand-built stubs — it was built to catch that patch class's gaps. Verify harness files byte-for-byte after transit.

**Environment**
- Cron has no `XDG_RUNTIME_DIR` → `systemctl --user` dies and the restart path silently no-ops. Export it; the single most critical env var here.
- Resolve hermes by absolute path: cron's PATH is narrower, and a missing binary misreads as "up to date".
- `set -u` + stripped env: guard `HOME`. A function called before its definition is "command not found" at runtime and `bash -n` won't catch it — define `notify()` first.
- A REPL session holds the drain: an in-tree `--yes` sits in "draining" until the turn ends, so expect the gateway restart to interrupt the session; check the receipt rather than re-running.
- Orphan-divergent installs back up HEAD to `refs/hermes-update-backups/orphan-main-*` then hard-reset. Rollback is a HUMAN decision — unattended auto-revert turns one bad update into a crash loop.
- Drain budget is max(restart_exit_wait_budget, 45s), up to 30 min with the default turn timeout. Fine under cron; don't add tighter script-side timeouts.
- `--yes` accepts config-migration and stash prompts non-interactively; `updates.non_interactive_local_changes: stash` protects local edits.
- Tirith blocks scripts containing `hermes gateway restart` / `gateway stop` even for `bash -n` — word around them or lint a copy.
- Never run an APPLY-mode tick in the agent's foreground terminal tool: the tool's own timeout (e.g. 420s) kills the whole process tree mid-`--yes` — the checkout lands (git hard-reset completes) but finalize/drain never run, so no receipt, no marker, gateway stays on old code. Run it `background=true` with a generous timeout, or just let the cron tick do it and verify after.
- A one-shot restart job in crontab must not pass arguments via CMD-line prefix assignments (`A=restart S=x systemctl --user "$A" "$S"`): cron's sh expands `$A` BEFORE the prefix assignments bind, systemctl gets empty verbs and dies silently (syslog shows the CMD fired; nothing happened). Put the assignments in a helper script as ordinary lines and schedule the script.
- **A config value is only delivered if the file it lives in is SOURCED.** `~/.hermes/.env` is read by the script ONLY for the bot token and chat id (grep `TG_ENV`): a `TG_PROXY=` line there reaches nothing. The v5.12 "primary fix" was written there, so the hardcoded 127.0.0.1:18089 default stayed armed for 18 days — yet every alert still arrived (the notify() fallback), so the only symptom was one "notify via proxy failed" line per tick, easy to misread as cosmetic. The real fix (v5.14) is `TG_PROXY=` in `~/.hermes/scripts/auto_update.env`, THE file the scheduler sources. Audit: `grep -c 'notify via proxy failed' ~/.hermes/logs/auto_update.log` must stop growing once fixed. When adding an override, assert where the script READS it, not just that it exists somewhere.
- Verify a host by REPRODUCING the scheduler's own delivery shape (`set -a; [ -f env ] && . env; set +a; AU_APPLY=1 script`) under `env -i` and printing what the script RESOLVES each knob to — `TG_PROXY` first, since `${TG_PROXY-default}` silently substitutes the hardcoded default for any host that never sets it. An env file holding only comments is exactly that case.
- notify() has a proxy→direct fallback (added 2026-09-17, to6429 incident: 14 consecutive notify failures because the hardcoded default proxy 127.0.0.1:18089 was a leftover from the Kimi sandbox where api.telegram.org is blocked; to6429 reaches Telegram directly). Contract: proxy attempt fails (curl exit≠0 or no "ok":true) AND TG_PROXY non-empty → one direct retry. Direct mode (empty TG_PROXY) has no fallback — correct, nothing to fall back to. A machine that CAN'T reach Telegram directly and lost its proxy still fails, but the dead-letter sentinel catches it (C6). Two fixes — and which one is live matters: ① `TG_PROXY=` (empty = direct, the `${TG_PROXY-default}` contract) must live in `auto_update.env`; the v5.12 copy placed in ~/.hermes/.env never reached the script (v5.14); ② the notify() fallback, which is what actually kept alerts alive since. Updater sha256 (v5.14) a6aff05b…, synced to the skill copy.
- Real-machine migration checklist: hardcoded endpoints (proxies, ports, service names) from the old host are silent landmines — the updater kept "working" (update success) while its only alert channel was dead for 14 ticks. Any monitor that counts consecutive failures should cross-check whether the counter growing means the check is failing or the environment migrated.

**Cross-host / WSL**
- `${VAR:-default}` treats an EMPTY value as unset — a legitimate setting like "no proxy, direct connection" is then silently replaced by the default. Use `${VAR-default}` when empty is a meaningful value. This shipped as a real bug: machines without the local proxy got pointed at a port that does not exist, and every notification vanished.
- A scheduler you assume exists may not run at all: WSL2 with systemd enabled can still have `cron` inactive, and a non-resident distro runs nothing (it terminates ~8 s after the last terminal closes). The failure is silent — the updater never fires. Log a preflight warning when the cron unit or gateway unit is inactive, and set `AU_CRON_UNIT=` (empty) when the host OS does the scheduling instead, so the warning is not permanent noise. `enable` is persistent, so cron returns by itself on each distro boot; missed ticks are NOT replayed, which is fine when the goal is "stay current while in use" rather than "run every tick".
- Windows copies must be LF-only; a CRLF `auto_update.sh` fails as `bad interpreter`. `/mnt/c/...` (DrvFs) has different permissions and git behaviour — keep the checkout on the Linux filesystem.
- Machine-specific defaults are written for one host. Before reuse elsewhere set `AU_REPO_DIR`, `AU_HERMES_BIN`, `TG_PROXY` (may be empty), `AU_GATEWAY_STATE`, `AU_GATEWAY_UNIT`, `AU_CRON_UNIT` — and make sure the schedule actually DELIVERS them (`set -a` around the source; see the delivery pitfall). See `references/wsl-deployment.md` for the probe list, scheduler residency, and the verify order.
- Per-host state and receipts are not interchangeable evidence; never ship one host's receipt as another's.
- When a new host breaks something, attribute the failure explicitly — code defect, environment property, or documentation gap — and say which. A parameterized value that cannot express a legitimate configuration (empty proxy = direct connection) is a CODE bug; a scheduler the platform never runs is an ENVIRONMENT property, and the docs must then state the residency requirement the design depends on. Reporting all three as "it works differently there" hides the one you can actually fix.

**Destructive actions are opt-in (the strongest available guard)**
- Rules in prose do not prevent this class of error; defaults and affordances do. The updater install is destructive (hard-resets the checkout, restarts the gateway), so the script runs REPORT-ONLY unless `AU_APPLY=1` is set. The scheduled invocation (cron / Task Scheduler) passes `AU_APPLY=1`; a smoke test, an installer, or an exploratory run cannot mutate the host even by accident. Verified: with the gate removed, S23 fails (a receipt IS written).
- The trade-off is the mirror risk: forgetting `AU_APPLY=1` in the scheduler turns "safe" into "never updates". Always assert the scheduled line carries it, and make the report-only path LOUD (`log` + stdout), never silent.
- An opt-in flag that gates the install path must be set by EVERY tool that drives that path — including support probes. After adding one, grep the whole bundle for callers, not just the script: the probes kept driving report-only ticks and reported "marker erased" / "not sanitized", false alarms that read as "the updater is broken". Make a probe say which it saw ("no install ran" vs "marker erased") so the reader hunts the right bug.
- A teeth test run in a polluted shell proves nothing. `export AU_APPLY=1` in a reproduce step leaked into the neutered copy and made it pass — the mutation looked ineffective. Unset what you set, run teeth under `env -u`, or the experiment measures your leftovers.
- A check that examines nothing must FAIL, not pass. A pointer check whose "fix" for false positives stripped inline code matched zero real paths and reported 0 broken while a referenced file was missing — a permanently-green check manufactures confidence. Count what you examined and fail on zero.
- Assert DELIVERY, not presence. A schedule shaped `AU_APPLY=1 . env; script` contains the text but never delivers the flag: an assignment prefixed to `.` binds to the source special builtin and is never exported to the child (bash: gone; dash/sh: lingers as a non-exported shell var). Either way the updater sees nothing and the schedule silently never updates. Put the flag on the script: `. env; AU_APPLY=1 script`. Grep-based checks pass the broken line — test the shape by running it under `bash` AND `dash` with a probe that reports what it inherited.
- Presence is not delivery for the OTHER variables either — the flag's fix can hide the config's failure. `. env; AU_APPLY=1 script` DOES deliver `AU_APPLY` (it is prefixed to the script), so an S24-style text check and S24b's flag probe both pass, while every value in the env file stays in the scheduler shell and never reaches a script that never sources it (verified by grep). `AU_REPO_DIR` / `AU_GATEWAY_STATE` / `AU_HERMES_BIN` then silently keep their defaults — and `TG_PROXY` survives only because the script carries a hardcoded default, i.e. exactly the migrated-endpoint landmine. A config file needs `set -a; [ -f env ] && . env; set +a;` (the `[ -f ]` guard so a missing file cannot abort the line before the flag is delivered), and the probe must assert what the CHILD inherited for every variable the file sets, in every shell a scheduler might use (`scripts/schedule_delivery.sh`).
- Apply the same shape to any other irreversible action: require an explicit flag, and make the default the harmless one.

**Installers**
- An installer must NEVER invoke the updater as a smoke test: it has no dry-run mode, so "test it" means "perform a real update". A preconditions-only install (unit active? cron enabled? token present? Telegram reachable?) is the correct shape. This bit once — an install run updated the host mid-session.
- An installer must derive paths from `$HOME`, never inherit an exported `HERMES_HOME`/`AU_*` from the calling shell, or it configures a different installation than the account it runs as.

**Delivery**
- **"Send me the updater zip" is a RELEASE, not a file copy.** Do not hand over whatever archive happens to sit on disk: re-derive the identity from the live deployment (`UPDATER_VERSION` and `sha256sum` of the installed script), reconcile the docs against it, then pack → verify on the EXTRACTED copy → send. An archive left from the previous release still passes every check (it was green when built) and ships the old code as if it were current; a bundle requested ad hoc may not exist on disk at all, in which case the absence of a `find` hit is the finding, not a blocker.
- Build bundles under `$HOME`, never `/tmp` (tmpfiles cleanup wipes them mid-session → curl exit 26 or an empty response). Require `"ok":true` in the Telegram API body before calling a send delivered — an empty response is not success.
- Pack/verify with PYTHON on hosts that ship no `zip`/`unzip` (the to6429 VPS is one), and set `ZipInfo.external_attr` explicitly: without it every +x bit is lost for the recipient, while the gate stays green because it runs scripts as `bash scripts/x.sh`. Check the modes STORED IN THE ARCHIVE against the SOURCE tree — python's `extractall()` does not apply them, so a check run on the extracted copy reports every executable as a mismatch. Recipe: `references/bundle-verification-recipe.md`.
- A send that returns HTTP 000: check the local file exists before blaming the network. A command that chains a file-producing step with the upload can be refused as a whole (approval timeout, security scan), so the earlier `cp` never ran and the upload fails on a missing file, not a dead proxy. Produce the artifact first, verify the path, then send in a separate command.
- Never restate in prose a number a command already prints (matrix tally, scenario count, log lines). Reference the artifact; hand-copied counts drift every incident.
- A bundle must carry every file its docs reference: a SKILL/README that points at `references/x.md` or `scripts/y.sh` makes the bundle broken when they are absent. After adding a pointer, re-derive the bundle's file list from the pointers and re-pack.
- Fix in ONE place, then sync in ONE direction, or a stale copy silently reverts the fix. Copying a whole directory (`cp -r src/. dest/`) over a tree that holds a newer fix overwrites it — after any bulk sync, re-run the affected probe and confirm the fix is still present in the shipped copy (`grep` for the fix's distinctive line). When two copies of a file diverge, `diff` BOTH directions before choosing the source of truth: the installed copy may hold a newer fix than the bundle, and blind one-direction copying drops it. The same holds for shipping: diff both directions before deciding which tree is the source of truth.
- Keep the two version identities separate: the updater's own `UPDATER_VERSION` (bundle filename) is unrelated to the Hermes version it installs. Notify as `✓ hermes agent updated to v<hermes> (updater v<UPDATER_VERSION>)`, and label any sample notification as stub or production — an unlabelled stub version reads as a production claim.

## Review-and-fix workflow

**Evaluate the deployment, not the bundle.** When asked to assess or audit the updater on a host, inventory EVERY scheduler surface that can fire it (root crontab, hermes cron jobs.json across ALL profiles, systemd user timers) and check enabled/paused state — a hermes-cron job paused through its own tooling stops updates with no further log line, so a log-based audit alone reads healthy while the updater is dead; the log stops, it does not object. Also diff the deployed scheduling mechanism against this skill's architecture rule (system cron, never hermes cron): a script can be technically green while registered by the exact mechanism it forbids. Two update stacks can coexist on one host (a legacy hermes-cron runner PLUS the system-cron script) — enumerate jobs by script NAME across all profiles, or the paused legacy stack hides behind the healthy one.

**Run the gate on the directory it ships in.** release_gate.sh must PASS from the deployed skill directory, not only from a packed bundle: its doc-pointer step checks files (README.md, install.sh) that live beside it, and a tree missing them is permanently red — the gate's PASS verdicts stop meaning anything until the tree carries every file its own checklist names.

**Grade the gate result honestly when asked to score the tooling.** A release gate that FAILs on its own deployed tree (missing README/install.sh) is a real finding, not a packaging footnote: report the failure, the concrete fix list, and the number, and separate it from the harness's methodology score. The same assessment should verify real production evidence (receipts: outcome distribution, SHA-advance proof per run) — an all-partial outcome history is fine IF every partial shows SHA advance, which distinguishes the documented drain race from a genuine install failure.

Run the reviewer's matrix against the UNPATCHED script first (reproduce the claims yourself), then apply critical patches, then hygiene, re-run to green, bump versions, add pitfalls, rebuild the bundle with `references/` and `verify/`. Distinguish real defects from packaging slips before accepting severity, and re-grade claims built on an incomplete sample.

Reproduce a claim before accepting it, and reproduce it with the reviewer's OWN tool. Do not accept a claim from its text alone — verify each one: some turn out overstated (a "no verification at all" claim about a receipt that in fact carries a SHA-verified snapshot), and a proposed fix can be worse than the bug (dropping a text gate entirely converts a false failure into a false success). State plainly which claims you verified and which you rejected, with the reason. When a reviewer's described reproduction cannot be reproduced as written, check the harness interaction first — a probe that self-seeds rebuilds its fixtures from the source argument, so any pre-patched state is silently reverted and the described steps may not reproduce; derive a faithful reproduction (neuter the SOURCE, pass its path to the probe) and state plainly what you could and could not reproduce.

Trace the config→wire path when asked what a setting "actually does": the user-facing parser, the clamp vocabulary, and the wire-shaping function may EACH transform the value, and a clamp table is not the last word. A "none" effort can mean the wire field is OMITTED entirely (so the server default — here medium — applies) rather than a literal `none` on the wire. The answer lives at the final wire fields, verified by driving the resolution function, not in the vocabulary table alone. Method: import the transport module directly (`sys.path.insert` the repo root), call the resolution + wire-fields functions with synthetic configs, and print the wire payload — every step is deterministic and needs no network.

Treat a reviewer's patch as a starting point, not a finished fix: re-derive the flag/lifecycle invariants and check each transition against how the script can die in between. Re-audit their patch with the same tools — the author is the person most blind to a patch's gap.

Audit the reviewer, not just the code: a careful pass still misses defects because trusted tools go un-audited, accepted evidence goes un-contracted, and happy paths go un-faulted. Each round finds what lives one epistemic level beyond the last sweep. The reviewer's own harness is an artifact to audit too — when it borrows the real machine's state, its green scenarios are false positives.

**Run what you are about to ship.** Before building a release bundle, execute every file that goes into it — the matrix, the probes, the support scripts — from the extracted copy, not from the working tree. Newly added tools are the least-tested part of a release and the most likely to be broken; a probe that cannot start is worse than no probe, because it looks like coverage.

**A teeth step can itself be toothless.** The gate's neuter is code too: a sed expression pasted into a double-quoted argument gets mangled by the shell (`$((10#...))` and `${#v}` expand at parse time), and the step still printed "teeth ok" because the probe failed on a copy broken in some *other* way — a false teeth pass in the one step that exists to prevent false coverage. Neuter by text edit from a file (a python `replace` with an `assert`, or `sed -f`), and assert the result actually DIFFERS from the source (`cmp -s`) before trusting the verdict. Then confirm the unbroken source PASSES the same probe, or the "teeth" may just be a probe that always fails.

**When to stop:** defect density per round is the signal. When a full round yields nothing new and the remaining candidates are theoretical, stop and let production run — real incidents are the only reviewer whose defect checklist isn't a subset of yours. Re-open on an alert firing, an upstream contract change, or a new environment to port to.

## Pre-publish checklist

1. LICENSE file in the bundle (frontmatter declaring MIT is not a licence file).
2. README opens with the support boundary + disclaimer: hard-resets a git checkout and restarts a gateway as root, unattended; Linux + systemd + git installs only; best-effort support.
3. `install.sh` — preconditions only (never runs the updater as a test) — or the install section becomes an issue generator.
4. Portability smoke test on a foreign layout (non-root `$HOME`, other repo path, no proxy, no user systemd). The no-systemd case must fail CLOSED.
5. Do NOT build a Docker matrix over historical Hermes versions — the script couples to five CONTRACTS (check banner, receipt schema, gateway_state fields, marker semantics, exit codes), not version internals, and upstream moves several commits a day. Detect contract drift instead.
6. The bundle self-describes its version in prose — README title, the `UPDATER_VERSION` line in its file list, the sha256 line. Re-derive each from the artifact at PACK time: a bundle naming the previous release ships false evidence, and no gate can see it, because the text is self-consistent and merely wrong.

## Publishing to GitHub

A repo push is a release: the same "re-derive from the live deployment" rule applies, plus public-exposure checks.

1. **Sync-check first**: `diff auto_update.sh ~/.hermes/scripts/auto_update.sh` must be identical, and the README's `UPDATER_VERSION` + `sha256` lines must match the shipped copy — pushing a stale tree publishes old code under a new-looking repo.
2. **Scan before public**: grep the whole tree for real secret VALUES (`ghp_[A-Za-z0-9]{20,}`, `xox[bap]-`, `PRIVATE KEY`, token strings — not variable names) and host identifiers (public IPs, hostnames). Hostname mentions inside incident notes are acceptable; live credentials and IPs are not.
3. **Re-run the gate on the exact tree being pushed** — the skill dir IS the shipped tree here, and it must stay whole: `release_gate.sh` checks README.md and install.sh exist beside it.
4. **Credential**: the user places the PAT themselves (never paste it in chat); reference it by variable name only (`$GITHUB_TOKEN` in the profile `.env`). `gh` may be absent — the REST API works with the same token: `curl -H "Authorization: token $GITHUB_TOKEN" -d '{"name":...,"private":false}' https://api.github.com/user/repos`, then `git push https://x-access-token:$GITHUB_TOKEN@github.com/<owner>/<repo>.git`. Never print the token; the remote URL carries it, so prefer a credential helper or a one-shot push over a persisted `origin` URL.
5. **Identity**: commit as `萤 (Firefly) <firefly@askclaw.dev>` — the getaskclaw publishing identity. The email must match the account's verified address or the commits don't count as contributions.

## Operating autonomy (user preference)

Minor operational decisions during maintenance — syncing a verified fix to the installed script, adding a gate step, rebuilding the bundle, running the verification chain — are ACTED ON directly once verified; do not poll the user for a go-ahead on reversible, low-blast-radius steps. Ask only when the action is irreversible, touches another host, or changes the schedule contract. "You nod and I'll sync" for a verified one-line fix is the anti-pattern; the verification chain IS the go-ahead.

## Notification design (user preference)

Silence when up to date. `✓` on install (headline the Hermes version, name the updater version), `✗` on failure, `⚠` when checks fail 3 consecutively then once per 24 further failures. Telegram via `$TG_PROXY` — which may be empty on hosts that reach the API directly — with creds from `~/.hermes/.env`.
